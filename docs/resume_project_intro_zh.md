# 简历项目介绍：轻量级工具调用 Agent 的强化学习与评估工程

> 基于当前代码 `731d3f6`、既有服务器验收反馈及相关论文/官方资料整理。本文只总结已完成工作，不推进开发或训练。
> 项目定位：**开源复现与工程改造**。主要可证明的贡献是评估稳定化、诊断体系和轨迹级奖励实现，而非已验证的模型能力大幅提升。

## 一、可直接写入简历的版本

### Qwen 工具调用 Agent 强化学习与评估优化

**技术栈：** Python、Qwen2.5-0.5B-Instruct、GRPO、LoRA、OpenPipe ART、vLLM、asyncio、pytest。

- 基于开源工程复现小参数模型工具调用 RL 流水线，在 **5 类确定性工具、12 类任务模板、200 条训练/50 条验证场景**上开展实验，补充基础设施失败、无工具调用及组内奖励方差诊断。
- 重构 checkpoint 评估，分离确定性评估与采样 Pass@8，采用分批限并发与独立推理参数；同一 step 2 检查点的已标记基础设施失败率由 **45% 降至后续实测 0%（下降 45 个百分点）**，完成 **50 场景 × 8 次采样 = 400 条 rollout**评估。
- 识别旧奖励将缺步调用误计为多步成功的问题，实现支持**调用次数/顺序、参数归一化、动态 observation 依赖**的 Reward V2，并提供同轨迹双评分及独立完整工具链判定，避免将评分规则变化误当成模型能力提升。

**使用说明：** 前两条已有服务器验证记录；第三条代码及测试用例已实现，但尚待服务器验收，不能据此声称 V2 已提升训练效果。

### 一句话介绍

围绕 0.5B 工具调用模型的 GRPO 实验，完成评估稳定化、故障诊断与轨迹级奖励改造，将一次评估中的已标记基础设施失败率从 45% 降至 0%，并建立区分采样成功、完整工具链与模型能力的评估口径。

## 二、完成了什么工作

| 工作 | 实现内容 | 当前证据/状态 |
|---|---|---|
| 训练与工具环境复现 | 使用既有 ART/GRPO/LoRA 主链路；工具调用后将结果回传模型，最多 6 轮交互 | 服务器已有 step 2 checkpoint；不把上游作者的训练结果归为个人成果 |

| 评估重构 | deterministic/sample/both 模式；按任务类型与预期调用深度统计；不完整返回立即报错 | Phase 2 服务器确认全套 PASS，最终具体测试数未记录 |
| 评估稳定化 | 默认 4 场景一批，批次顺序执行；采样模式并发上界为 `4 × k`；评估关闭 logprobs | 同一 step 2 上完成 50 条确定性和 400 条采样轨迹，均无已标记 infra failure |

工具环境为计算器、天气查询、知识库搜索、单位转换和国家数据查询，均使用本地确定性实现，**不是接入真实外部服务的生产 Agent**。训练/验证场景沿用仓库既有数据，不冒称个人重新构建的独立 benchmark。

## 三、量化结果：哪些能写，哪些不能写

### 1. 已观测到的工程改善

对比使用同一个 step 2 checkpoint、50 个场景、每场景 8 次采样：

| 指标 | Phase 1 评估 | Phase 2 采样评估 | 解释 |
|---|---:|---:|---|
| 总尝试数 | 400 | 400 | 分母不变 |
| 已标记基础设施失败 | 180/400，45% | 0/400，0% | **下降 45 个百分点**；仅代表这两次运行的观测结果 |
| 未标记失败的轨迹数 | 220 | 400 | 增加 180 条，相对增加 **81.8%**；不等于正确轨迹增加 |

推荐简历使用“失败率下降 45 个百分点”这一表述。这里比较的是**评估工程的稳定性**，不是重新训练后的模型收益；限并发、生成参数与 logprobs 策略同时调整，不能把改善全部归因于某一个措施，也不能保证以后永不失败。

### 2. 当前 checkpoint 的能力观测

以下成功定义都是旧版 **`reward > 2` 代理判定**，不是最终答案正确率，也不是完整工具链成功率。

| 指标 | 实测结果 | 分母与含义 |
|---|---:|---|
| 确定性奖励阈值成功率 | **22%** | 11/50 个场景，一次尝试 |
| 观测 Pass@8 | **30%** | 15/50 个场景，8 次采样至少一次超过奖励阈值 |
| 采样 rollout 成功率 | **21%** | 84/400 条轨迹超过奖励阈值 |
| 确定性 no-tool rate | **6%** | 3/50 条轨迹无工具调用 |
| 采样 no-tool rate | **14%** | 56/400 条轨迹无工具调用 |

这些数字适合用于面试解释当前基线，不建议脱离判定条件直接写成“任务准确率 30%”。尚无固定评估口径下的训练前后或 V1/V2 训练对照，**目前无法量化模型能力提升了多少**。

### 3. 不应使用的“提升”表述

- 不写“准确率从 README 的 4.5% 提升至 22%/30%”：README 是上游作者的 step 15 实验，checkpoint、采样口径和运行条件均不同。
- 不写“14.8% → 21%，模型能力提升约 42%”：前者包含 45% 已标记失败，后者没有；且两次是同一 checkpoint，不是模型训练前后对照。
- 不写“多步成功率 100%”：确定性结果里的 3 个 `country_compare` 成功存在缺步假阳性。
- 不写“V2 提升准确率/训练效率 X%”：尚未完成 V2 服务器验收和训练对照。
- 不写“推理加速 X 倍、训练成本降低 X%”：没有时延、吞吐或成本的可比测量。

## 四、主要亮点及面试解释

### 亮点 1：把评估稳定性与模型能力分开

**问题：** 网络、推理服务或后端异常得到低 reward 后，很容易被混同为模型不会调用工具。

**实现：** 依据现有 `failed == 1` 标记单列基础设施失败；同时保留全部尝试分母和有效轨迹统计，不静默删失败样本或重采样。独立 checkpoint 评估使用顺序场景批次，并与训练的探索参数分离。

**价值：** 在同一 checkpoint 上观测到失败率下降 45 个百分点，使模型能力分析不再被大量已标记异常淹没。但诊断仅识别现有标记，不声称已精确覆盖所有异常类型。

**代码：** [`src/diagnostics.py`](../src/diagnostics.py)、[`scripts/eval_checkpoint.py`](../scripts/eval_checkpoint.py)。

### 亮点 2：区分 Accuracy、Pass@k 与 rollout 成功率

**问题：** 400 条轨迹的成功比例，不能直接当成 50 个任务的 Pass@8；一次确定性尝试与 8 次采样也不应混比。

**实现：** deterministic 每场景一次，sample 每场景 k 次；分别输出任务级成功比例和轨迹级成功比例，按 1/2/3 次预期调用分层。旧字段保留，报告注明成功定义及采样参数。

**价值：** 同一 checkpoint 同时得到 22%、30% 和 21% 三种不同口径的指标，明确各自分母；框架返回缺组、缺尝试时直接报错，避免缩小分母产生虚高结果。

**代码/说明：** [`docs/phase2_evaluation_zh.md`](phase2_evaluation_zh.md)、[`tests/test_evaluation.py`](../tests/test_evaluation.py)。

### 亮点 3：从单调用相似度升级为轨迹级 Reward V2

**问题：** 旧评分用工具名集合比较，重复工具调用被去重，缺一步仍可能超过成功阈值；字符串精确匹配也无法正确处理格式差异及 `__dynamic__` 参数。

**实现：** 将奖励拆为格式、工具多重集、序列、参数键、参数值及完成度六个维度；重复调用分别计数，正确前缀获得部分 credit。数值使用 Decimal 归一化，数学表达式使用受限 AST 比较；未完成调用链的总奖励限制为 **≤2**，完整正确轨迹最高 **+4**，总范围保持 **[-3,+4]**。

**价值：** 针对“只做一步也算完成”的评估漏洞提供明确约束，同时保留部分正确行为的训练信号。这是已实现的评分机制，不是已经证明有效的训练提升。

**代码/状态：** [`src/reward_v2.py`](../src/reward_v2.py)；待服务器验收。

### 亮点 4：验证动态参数确实来自前一步 observation

**问题：** 工具参数碰巧命中某个数字，不代表模型利用了前一步执行结果；同一 assistant 回复中同时生成依赖调用，也看不到该回复内工具的返回值。

**实现：** 旁路 trace 保存 `{name, arguments, result, turn}`；动态参数只匹配受支持的前一步结果及字段，例如天气的 temperature，而不是 humidity。实际 rollout 要求消费调用的 assistant turn 严格晚于生产调用，并核对单位与调用对齐。

**价值：** 将“数字匹配”与“有执行时序证据的结果复用”区分开，减少动态依赖误判。当前仅支持明确实现的路由，不做任意语义判断。

**代码/状态：** [`src/rollout.py`](../src/rollout.py)、[`src/reward_v2.py`](../src/reward_v2.py)；待服务器验收。

### 亮点 5：用同一轨迹审计评分变化，保留训练兼容性

**实现：** 同一执行 trace 同时计算 V1/V2，不重复生成或执行工具；独立 `complete-tool-chain-v1` 检查次数、顺序、参数、动态依赖与有效结果。trace 按 trajectory 对象身份绑定，避免组内重排错配；V1 默认保留，原始 Choice/logprobs 不因审计而丢失。

**价值：** 将“换评分器后分数变高”与“模型真的变好”分开，为后续受控对照提供工具。独立 checker 衡量的是预期工具协议，仍不等于最终答案正确性。

**代码/状态：** [`scripts/eval_checkpoint.py`](../scripts/eval_checkpoint.py)、[`tests/test_phase3_integration.py`](../tests/test_phase3_integration.py)；待服务器验收。

## 五、技术栈与职责

| 层次 | 技术 | 项目中的用途 |
|---|---|---|
| 基础模型 | Qwen2.5-0.5B-Instruct | 约 0.5B 参数的指令模型，生成工具调用 |
| 学习算法 | GRPO | 同场景多条轨迹组成比较组，以组内相对奖励提供学习信号 |
| 参数高效训练 | LoRA | 由 ART 后端管理适配器训练及加载 |
| 训练编排 | OpenPipe ART `0.5.17` | Trajectory/TrajectoryGroup、训练更新、checkpoint 与日志 |
| 推理服务 | vLLM、OpenAI-compatible API | 生成模型回复与工具调用；训练保留原始 Choice/logprobs |
| 后端生态 | PyTorch、TRL、Unsloth、Transformers | ART 后端管理的训练与模型组件，不是自行重写的训练器 |
| 工程与验证 | Python、asyncio、JSONL、YAML、pytest/pytest-asyncio | 异步执行、配置、可审计数据与回归测试 |

RunPod、CUDA/GPU 和 uv 是仓库记录的部署/安装方案，不据此断言用户服务器的实际 GPU 型号。简历不建议写死定制 vLLM 小版本：仓库记录 `0.17.0+art1`，本次查阅的 ART `v0.5.17` 官方依赖文件声明 `vllm==0.17.0`；缺少实际服务器环境清单时，不能替其证明具体 wheel 来源。

3. **[OpenPipe ART v0.5.17 官方 README](https://github.com/OpenPipe/ART/blob/v0.5.17/README.md)**：说明 Trajectory → 分组 → GRPO → LoRA checkpoint → vLLM 加载的训练循环；[对应依赖文件](https://github.com/OpenPipe/ART/blob/v0.5.17/pyproject.toml)用于核对后端生态。
